# `nanne`：電気通信事業法の届出条件と開発スケジュールへの影響

**作成日: 2026-08-18**

> **法務上の注意**：これは公開一次情報に基づく実務用の整理であり、法的助言ではありません。実際の公開前には、収益性、構成図、データフローおよび運営主体を示して、管轄の総合通信局に届出・登録の要否を確認してください。

## エグゼクティブサマリー

`nanne` の「招待URLで参加者を特定し、利用者同士がテキストを送受信する」機能は、総務省が例示するダイレクトメッセージや参加者限定のWeb会議に近く、**他人の通信の媒介**に当たり得ます。[1]

ただし、メッセージ機能を実装した時点で直ちに届出が確定するわけではありません。総務省ガイドブックの整理では、次の4条件を満たして初めて「電気通信事業を営む者」に該当します。特に、**料金・広告等を通じて利益を得ようとするか**が、`nanne` の公開計画を分ける最初の判断点です。[1]

| 条件 | 公式ガイドの意味 | `nanne` v1での確認点 |
| --- | --- | --- |
| 他人のための提供 | 自己利用ではなく、他人の需要に応じて役務を提供する。 | 第三者が招待URLで参加できる公式サービスか。 |
| 利益を得ようとすること | 料金を取る場合だけでなく、無料でも広告収入を得る場合を含む。無償・原価ベースは該当しないと説明されている。 | 利用料、広告、紹介料、スポンサー、寄付の扱いを公開前に固定する。 |
| 電気通信設備の利用 | 自己所有に限らず、利用権限を持つサーバー等を含む。 | アプリ、クラウド、DB、WebSocket、CDN/WAF、ログ基盤の構成。 |
| 反復継続 | 緊急・臨時の提供ではなく、主体的・継続的な提供。 | 継続公開、利用規約、サポート、障害対応、運営体制があるか。 |

## 1. 届出が必要になる具体的な条件

### 1.1 `nanne` に当てはめた判断

下表は、現在の想定を前提にした実務上の判断表です。ここでいう「届出が必要」は、登録対象ではないことを前提にした法16条の届出を指します。自ら設置する電気通信回線設備の規模・区域が所定基準を超える場合等は、届出ではなく**登録**が必要になり得ます。[2]

| 運用パターン | 届出・登録の見込み | 理由と次の行動 |
| --- | --- | --- |
| 開発環境、社内検証、自己利用 | 通常は低い。 | 他人の需要への反復継続提供に当たらない可能性が高い。ただし公開用インフラ・広告・一般利用を開始する前に再判定する。 |
| 無料、広告なし、原価回収を超える利益を意図しない招待制ベータ | 必要性は低い可能性があるが、事実確認が必要。 | 総務省ガイドブックは無償・原価ベースを「利益を得ようとする」に当たらないと説明する。収益化の予定、運営目的、構成を記録し、管轄局へ照会する。 |
| 有料の招待制チャット | **届出または登録が必要となる可能性が高い。** | 他人の通信を媒介し、利益を得る意図を伴う継続サービスだからである。開始前に登録・届出を確定する。 |
| 無料だが広告収入があるチャット | **届出または登録が必要となる可能性が高い。** | 総務省は、無料サービスでも広告収入で利益を得ようとする場合を届出が必要となる例として示す。[1] |
| OSSコードだけを配布し、開発者のサーバーやAPIが通信を通さない | コード配布者自身の届出は通常不要と考えられる。 | 実際に利用者間チャットを提供するself-hosted運営者が、自らの運用について確認する。 |
| 共通の公式API、リアルタイムリレー、DB、ログ、モデレーションを提供 | 公式運営者について届出・登録の検討が必要。 | 誰が通信・データを扱うかで、OSS配布者ではなくサービス提供者として評価する。 |

**小規模・招待制・Cloudflare利用は、単独の免除条件ではありません。** 招待された少人数がいることは「専ら一者への提供」と同義ではなく、クラウド利用も通信媒介の検討をなくしません。[1] [2]

### 1.2 届出か登録か

法9条は原則として登録を求めますが、設置する電気通信回線設備の規模・区域が省令基準を超えない場合等は登録対象から除かれます。登録対象ではない電気通信事業を営む者は、法16条により届出を行います。[2]

`nanne` のようなWebアプリについて、クラウド・CDNを利用しているだけで登録か届出かが自動的に決まるわけではありません。相談時には、事業者自身が何を設置・利用・管理しているか、特に伝送路・交換設備に該当し得る設備の有無を、構成図で説明してください。通常の小規模Webチャットでは、登録より届出の可能性を先に確認する設計が現実的ですが、これは構成確定後に管轄局が判断する事項です。

### 1.3 届出のタイミングと内容

e-Govの案内では、法16条の届出は**事業開始前**に提出し、手数料はありません。個人・法人の別と電気通信回線設備の設置の有無で様式が分かれ、回線設備を設置する者には別途の自己確認届出等が必要となる旨が案内されています。[3]

| 届出前に確定する事項 | 開発上の意味 |
| --- | --- |
| 運営者の氏名・名称、住所、問い合わせ先 | 個人事業・法人化、問い合わせ用メール、規約の名義を先に決める。 |
| 業務区域 | 日本向けか、海外利用をどう扱うかを明確にする。 |
| 電気通信設備の概要（該当する場合） | 本番アーキテクチャ、クラウド、リアルタイム接続、ネットワーク構成を固定する。 |
| 収益モデル | 有料、広告、スポンサー、寄付の扱いを、公開後に曖昧なまま変更しない。 |
| データフロー | 本文、IPアドレス、Cookie、ログ、バックアップ、監視の保存先と権限を確定する。 |

## 2. 開発計画にどう影響するか

届出の有無は、チャットUIの実装そのものを止める要因ではありません。一方で、**公式サービスを公開する前**に収益モデル・運営主体・本番構成を確定しなければ、行政相談、届出書、プライバシー通知、利用規約、ログ設計を確定できません。したがって、開発計画では「機能開発」と「公開可否判定」を分離し、後者をリリースゲートとして扱うべきです。

### 2.1 先に凍結すべき5つの意思決定

| 意思決定 | なぜ先に必要か | 推奨期限 |
| --- | --- | --- |
| v1の収益性 | 無料・原価ベースか、広告・課金等を含むかで届出判断が大きく変わる。 | 実装開始時、遅くとも公開6週間前。 |
| 運営主体 | 誰が届出・規約・問い合わせ・データ保護を担うかを決める。 | 公開6週間前。 |
| 本番アーキテクチャ | 設備概要、委託先、データフロー、海外処理を説明する前提になる。 | 公開5週間前。 |
| データ保持・管理者アクセス | 通信の秘密、プライバシー通知、バックアップ、通報対応の設計前提になる。 | 公開4週間前。 |
| 外部サービス | CDN/WAF、分析、エラー監視、メール、課金を導入すると送信データと説明が変わる。 | 公開4週間前。 |

### 2.2 実装と並行できること

以下は、届出要否の回答を待たずに着手できます。むしろ先に実装しておくと、届出が必要になった場合にも公開準備の手戻りを抑えられます。

| 領域 | v1で実装・決定すること | 法務・運用上の効果 |
| --- | --- | --- |
| 招待URL | 十分に推測困難なトークン、失効、再発行、利用回数または期限の制御。 | URL流出時の被害範囲を限定する。 |
| 本文アクセス | 通常運用では本文を読まない。例外閲覧は目的・承認・記録を必須にする。 | 通信の秘密に配慮した最小権限設計になる。 |
| ログ | 本文をログ・監視イベントへ送らず、IPや識別子も必要最小限・短期間にする。 | 個人情報・漏えい・外部送信のリスクを下げる。 |
| 削除 | 本文、ルーム情報、ログ、バックアップを分けて保持期間と削除処理を定義する。 | 「一定期間後に消える」の説明を正確にできる。 |
| 通報・停止 | 通報受付、ルーム停止、URL失効、証跡保全、緊急連絡を用意する。 | 違法・権利侵害・不正利用への初動を可能にする。 |
| 外部SDK | 広告、第三者解析、不要な監視SDKはv1から除外する。 | 外部送信・委託先の説明と同意設計を最小化する。 |

### 2.3 リリースを止めるべき変更

次の変更は、単なる機能追加としてリリースせず、電気通信事業の該当性・届出事項・プライバシー通知を再確認するゲートを設けてください。[2]

| 変更 | 再評価する理由 |
| --- | --- |
| 有料化、広告、スポンサー導入 | 「利益を得ようとする」要件と届出判断に直接影響する。 |
| 公開ルーム、検索、タイムライン | 通信の宛先・公開範囲・違法情報対応の前提が変わる。 |
| 共通API、リレー、認証、DBの提供 | OSS配布者とサービス提供者の役割分担が変わる。 |
| 画像、動画、ファイル、音声・映像 | 保存データ、権利侵害、違法コンテンツ、セキュリティの影響が増える。 |
| 海外向け提供、海外インフラ追加 | 業務区域、外国第三者、越境データ、利用規約の前提が変わる。 |
| 分析・広告・外部SDK導入 | 利用者情報の外部送信と通知・公表等の検討が必要になる。[4] |

## 3. 推奨スケジュール

ここでは、**本日をWeek 0として、最短で6週間の公開準備枠を確保する**案を示します。これは行政の法定審査期間を保証するものではなく、事実整理、管轄局への相談、必要な届出、文書・運用・技術の整合を確保するためのプロジェクト上のバッファです。

### 3.1 収益化を伴う公式サービスの場合

| 時期 | 法務・行政 | 開発・運用 | リリース判定 |
| --- | --- | --- | --- |
| Week 0 | 収益モデルと運営主体を決定する。 | v1の機能凍結案、データ項目一覧を作る。 | **課金・広告の有無を確定する。** |
| Week 1 | 構成図、通信フロー、設備・委託先一覧、保存期間表を作る。管轄局への相談資料を準備する。 | 招待URL、本文非記録ログ、削除ジョブ、管理者権限を実装する。 | 相談資料が1枚で説明できるか確認する。 |
| Week 2 | 管轄の総合通信局へ、届出か登録か、回線設備の自己確認の要否を相談する。 | 本番候補環境でデータフローを検証する。 | 公式回答・案内に従い、手続ルートを確定する。 |
| Week 3 | 届出対象なら届出書を完成し、開始前に提出する。追加書類・自己確認の要否を確認する。 | 規約、プライバシー通知、削除方針、通報手順、漏えい対応手順を完成する。 | **届出が必要なら、提出完了が公開の前提。** |
| Week 4 | 変更時・廃止時の責任者と手順を決める。 | レート制限、障害対応、権限監査、バックアップ削除をテストする。 | 本番構成が届出・通知内容と一致するか確認する。 |
| Week 5 | 問い合わせ導線と記録を確認する。 | 少人数のクローズドベータを行い、ログ・削除・通報を運用テストする。 | 収益性・構成・外部SDKの変更がないことを確認する。 |
| Week 6 | 公開前の最終確認を行う。 | 本番公開、初週の監視と問い合わせ当番を開始する。 | 公開する。 |

この経路では、**Week 2までに行政相談、Week 3までに必要な届出の提出**を完了させる設計です。行政から追加確認が来た場合に備え、公開日はWeek 6以降に固定し、届出提出日より前には一般公開・課金・広告開始をしないでください。

### 3.2 無料・広告なし・原価ベースのベータの場合

無償・原価ベースで利益を得る意図がないと明確に設計・運用できるなら、総務省ガイドブックの「営む」要件を満たさない可能性があります。[1] ただし、実際に届出不要と決め打ちするのではなく、Week 1〜2の相談・確認は維持してください。ここで短縮できるのは届出書の作成・提出工程であり、通信の秘密、個人情報、外部送信、削除、通報といった開発タスクではありません。

| 時期 | 実施内容 |
| --- | --- |
| Week 0 | 無料・広告なしの方針と、将来の収益化は公開前に再判定するルールを決定する。 |
| Week 1 | 構成図、データフロー、保存・削除、運営主体を整理し、管轄局へ確認する。 |
| Week 2〜3 | チャット、招待URL、削除、ログ最小化、通報・停止、規約・通知を実装する。 |
| Week 4 | クローズドベータで、削除、アクセス権限、障害・通報手順を検証する。 |
| Week 5 | 管轄局への確認結果と本番構成の一致を最終確認し、公開する。 |

無料ベータから広告・課金へ移る日は、単なる機能リリースではなく、**届出要否を再判断する別プロジェクトの開始日**として扱うべきです。

## 4. 公開可否のゲート

公開予定日の2週間前に、次のゲートを設けてください。1つでも未決なら、機能を削ってでも公開を遅らせるか、限定ベータに留めます。

| ゲート | 合格条件 |
| --- | --- |
| 収益性 | 料金・広告・その他収入の有無が文書化され、公開後に変わらない。 |
| 行政手続 | 管轄局に相談済みで、必要な登録・届出・自己確認の手続が開始前に完了している。 |
| 本番構成 | 構成図と実環境が一致し、委託先・リージョン・権限が説明できる。 |
| 通信の秘密 | 本文への通常アクセスがなく、例外閲覧に承認・記録・期間制限がある。 |
| データ通知 | プライバシー通知に取得項目、目的、外部送信、保存・削除、問い合わせ先がある。 |
| 運用 | 招待URL失効、通報、ルーム停止、漏えい、障害、法的要請の担当と手順がある。 |
| 変更管理 | 課金・広告・外部SDK・公開機能の追加時に再評価する責任者が決まっている。 |

## 5. 今すぐ決めるべき結論

開発を止めずに進めるため、次の順で決めるのが合理的です。

1. **v1は無料・広告なし・外部解析なしで出すか、有料・広告付きで出すかを決める。** 後者なら届出・登録を要する前提でWeek 1の相談に進む。
2. **公式版の運営主体を決める。** 個人・法人、問い合わせ先、クラウド契約主体、利用規約の名義を統一する。
3. **本番構成を凍結する。** CDN/WAF、アプリ、リアルタイム接続、DB、バックアップ、監視を一枚の図にする。
4. **通信本文を読まない運用を標準にする。** 管理者アクセスは、通報・障害・法的要請に限定し、記録を残す。
5. **公開日を、行政相談・必要な届出・運用テストの後に置く。** 届出要否が未確定のまま、課金や広告を伴う一般公開はしない。
