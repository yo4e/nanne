# `nanne` 公開前法務・運用レビュー

**調査日: 2026-08-18**

> **位置づけ**：本書は、アカウント不要・招待URL・少人数・テキストのみ・一定期間後削除を想定する `nanne` v1 の公開前レビューです。AIによる公開情報の整理であり、個別案件の法的判断ではありません。公開時の運用事実と構成図を添え、管轄の総合通信局および必要に応じて弁護士・弁理士に確認してください。

## 結論

`nanne` を日本で小さく公開するために最も重要なのは、**収益性を含む電気通信事業への該当性を公開前に確定すること**、**通信の秘密を前提にデータアクセスを最小化すること**、そして**利用者にデータ利用と削除方針を分かりやすく示すこと**です。招待制・少人数・無料という設計はリスクを下げ得ますが、それだけで届出、個人情報保護、外部送信、違法利用対応を不要にはしません。[1] [2]

総務省のガイドブックによれば、`nanne` 型の宛先を指定した利用者間メッセージ機能は「他人の通信の媒介」に当たり得ます。利益を得ようとし、他人のために、電気通信設備を用いて、反復継続して提供するなら、登録または届出が必要な電気通信事業に該当する可能性が高い整理です。無償・原価ベースで利益を得る意図がない運用は、この「営む」の要件に当たらない可能性がありますが、公開時の実態を添えて確認してください。[1]

| v1公開の優先度 | すべきこと | 目的 |
| --- | --- | --- |
| **必須** | 収益性、運営主体、通信フロー、設備・委託先を確定し、電気通信事業の登録・届出要否を総合通信局に確認する。 | 法令上の手続を公開前に確定する。 |
| **必須** | 利用規約、プライバシー通知、保存・削除方針、問い合わせ先を公開する。 | 利用条件とデータ利用を透明化する。 |
| **必須** | 本文・通信メタデータへの管理者アクセス、ログ、バックアップ、通報、法的要請の手順を文書化する。 | 通信の秘密と安全管理を実装・運用で守る。 |
| **必須** | 実際に送信されるデータを棚卸しし、Cloudflare、ホスティング、監視、分析等の委託先・保存地域を特定する。 | 個人情報、外部送信、委託先管理を判断可能にする。 |
| **強く推奨** | 招待URLの十分なランダム性・失効、レート制限、通報、ブロック、緊急停止を設計する。 | 悪用・漏えい・権利侵害の被害範囲を限定する。 |
| **強く推奨** | v1では広告・第三者解析・不要なSDKを入れず、外部送信を最小化する。 | 利用者への説明負担と情報流出面を減らす。 |
| **将来再評価** | 有料化、広告、公開ルーム、検索、ファイル送信、音声・映像、海外展開、共通バックエンドを追加する。 | 役務、データ、消費者保護、著作権・違法情報対応の前提が変わるため。 |

## 1. 電気通信事業法

### 現時点の判断

電気通信事業法は、電気通信設備を用いて他人の通信を媒介すること等を「電気通信役務」、その役務を他人の需要に応じて提供する事業を「電気通信事業」と定義します。[3] 総務省は、情報を本質的に加工せず、送信時に受信者を宛先として指定して他人同士を通信させる形を媒介と整理し、メール、ダイレクトメッセージ、参加者限定Web会議、ビジネスチャットを例示しています。[1]

`nanne` v1は、招待URLを通じて少人数の宛先へテキストを送る構想であるため、このメッセージ媒介の整理に近いと考えるのが安全です。総務省の同資料は、他人のための提供、利益を得ようとすること、電気通信設備の利用、反復継続の全要件を満たす場合に「電気通信事業を営む者」に該当すると説明します。料金だけでなく、無料サービスに広告収入を伴わせる場合も利益を得ようとするケースとして案内されています。[1]

| 判断要素 | v1で確定すべき事実 | 対応 |
| --- | --- | --- |
| 提供主体 | OSS配布者、公式サービス運営者、導入先の誰が利用者に役務を提供するか。 | サービス画面、規約、問い合わせ先、インフラ契約主体を一致させる。 |
| 収益性 | 利用料金、広告、紹介料、スポンサー、寄付、原価回収を超える収益意図の有無。 | 公開前に方針を固定し、追加する前に再判定する。 |
| 通信形態 | 送信者・受信者、宛先指定、本文の加工の有無、公開閲覧の可否。 | データフロー図と仕様書にする。 |
| 反復継続性 | 一時検証か、一般利用者向け継続サービスか。 | ベータ公開を含め運用期間・対応体制を説明する。 |
| 設備 | アプリ、CDN/WAF、リアルタイム基盤、DB、ログ、バックアップを誰が管理するか。 | 構成図、リージョン、権限、委託先を整理する。 |

登録対象でない電気通信事業を営む場合は、法16条の届出が必要となり得ます。e-Govは届出を開始前・手数料なしとし、個人・法人および回線設備設置の有無により様式を分けています。回線設備を設置する場合には、別途の自己確認届出等が必要となる旨も案内されています。[4]

### 通信の秘密

法3条は検閲を禁止し、法4条は電気通信事業者の取扱中に係る通信の秘密を保護します。さらに法164条3項は、同条1項の適用除外の事業を営む者についても、法3条および4条を適用します。[3] したがって、適用除外と判断した場合でも、本文と通信メタデータを無制限に閲覧・利用できるものではありません。

v1では、通常運用で本文を読まない設計を原則とし、通報、安全対応、障害調査、法的要請のそれぞれについて、閲覧条件、承認者、対象範囲、アクセス記録、保存期間を定めてください。招待URLは秘密情報として扱い、ログに全文URLを残す場合にもアクセス権限と保持期間を限定します。

## 2. 個人情報・ログ・委託先

個人情報保護委員会の通則ガイドラインは、個人情報データベース等を事業の用に供する者に、規模や営利・非営利を問わず適用され得ると説明します。個人情報が少ない小規模サービスでも、利用目的の特定・通知または公表、安全管理措置、従業者・委託先の監督、保有個人データへの対応等を、実際に取り扱うデータに応じて設計する必要があります。[5]

メッセージ本文、表示名、問い合わせ内容、IPアドレス、端末・ブラウザ情報、Cookie、ルームID、アクセスログは、単独または容易に照合できる情報と組み合わさることで個人情報または個人関連情報になり得ます。特にチャット本文には、本人が自ら健康、信条、犯罪被害等を記載する可能性があります。サービスが意図して収集しなくても、事故時の影響が大きい情報を含み得る前提で扱ってください。[5]

| データ類型 | 目的を限定して記載する例 | v1の最小化方針 |
| --- | --- | --- |
| メッセージ本文 | ルーム参加者への表示、通報対応、障害復旧。 | 保持期間を短くし、通常は管理者が読まない。 |
| 招待URL・ルームID | 入室管理、失効・不正利用対応。 | 十分な推測困難性を持たせ、ログでの露出を抑える。 |
| IP・アクセスログ | セキュリティ、レート制限、障害調査、不正利用対応。 | 必要項目だけを短期間保存する。 |
| Cookie・ローカル保存 | セッション維持、入室状態、セキュリティ。 | 広告・行動追跡を入れず、目的を明記する。 |
| 問い合わせ・通報 | 連絡、調査、対応履歴。 | 受付窓口を分離し、閲覧者を限定する。 |

漏えい等が起きた場合、要配慮個人情報を含む事態、財産的被害のおそれ、不正目的による漏えい等、または1,000人超の漏えい等では、個人情報保護委員会への報告と本人への通知が必要です。PPCは速報を概ね3〜5日以内の目安として案内しています。[6] v1公開前に、検知、封じ込め、証跡保全、影響評価、通知、問い合わせ対応の担当と連絡経路を決めてください。

### Cloudflare等への委託・海外処理

外部インフラを使う場合、委託か第三者提供か、外国にある第三者への提供に当たるかは、契約と実際のデータ処理によって判断します。サービス提供者、CDN/WAF、クラウド、ログ・エラー監視、メール、サポートの各サービスについて、事業者名、契約主体、保存・処理地域、送信データ、目的、削除方法を一覧にしてください。個人データの委託では、委託先監督も必要です。[5]

## 3. Cookie・外部送信

メッセージ媒介サービスは、総務省が「利用者の利益に及ぼす影響が少なくない電気通信役務」として列挙する対象です。このため、利用者端末から情報を外部送信させるプログラム等を送る場合、原則として、送信される情報の内容、取扱者の氏名または名称、利用目的を、通知・容易に知り得る状態への設置・同意取得・オプトアウトのいずれかで確認可能にする必要があります。[2] [7]

サービス提供に真に必要な情報や、事業者が利用者へ送った識別符号（first-party cookieのID）には例外があります。しかし、広告、第三者アクセス解析、行動計測、不要なエラー監視などは、必要性を個別に検討しなければなりません。[8]

| 外部送信の候補 | v1の方針 | 公開時の確認 |
| --- | --- | --- |
| ルーム利用に必要な自社サーバー送信 | 必要最小限に限る。 | 送信項目と目的が役務提供に真に必要かを確認する。 |
| first-party session cookie | 安全なセッション維持に限る。 | 属性・有効期間・目的を整理する。 |
| CDN/WAF | セキュリティ・配信に必要な範囲で使う。 | 送信先、IP等の送信項目、契約・保存地域を通知に反映する。 |
| 第三者解析・広告SDK | **v1では導入しない。** | 導入する場合は外部送信規律とプライバシー通知を事前に再評価する。 |
| エラー監視 | 本文を送らない設定を優先する。 | 送信イベント、マスキング、保持期間、送信先を確認する。 |

## 4. 利用規約・プライバシー通知・削除方針

個人情報保護法に「プライバシーポリシー」という名称のページを一律に要求する規定があるわけではありません。ただし、利用目的等を通知・公表し、問い合わせ・権利行使の窓口を示すため、公開サービスでは実質的に必要です。[5]

v1では、少なくとも次を公開画面から容易に到達できるようにしてください。

| 文書 | 最低限の内容 |
| --- | --- |
| プライバシー通知 | 運営者、取得データ、利用目的、委託先・外部送信、保存期間、削除、問い合わせ、保有個人データへの対応。 |
| 利用規約 | 禁止行為、招待URLの取扱い、利用停止、通報、免責の範囲、準拠法・連絡先。 |
| 削除方針 | 本文、ルーム、ログ、バックアップごとの保持期間と削除処理の関係。 |
| 安全・通報ポリシー | 通報方法、緊急時の制限・停止、著作権・プライバシー侵害等の受付、対応の限界。 |

「一定期間後に消える」と表現する場合、本文の削除だけでなく、検索索引、キャッシュ、監視ログ、バックアップからの消去時期を区別して説明してください。即時に全ての複製から消える設計でない限り、そのように断定しないことが重要です。

## 5. 違法情報・権利侵害・未成年者

`nanne` v1は公開タイムライン・検索・一般公開投稿を持たないため、大規模なプラットフォーム向け制度の指定対象に直ちに当たるとは限りません。しかし、招待URLが流出すれば、嫌がらせ、脅迫、個人情報、著作権侵害、違法な画像・リンク等が送られる可能性はあります。

v1では、禁止行為、通報窓口、招待URL失効、ルーム停止、再発防止、緊急連絡の方針を定めてください。本文を読まない原則と、安全対応で例外的に確認する条件は、通信の秘密への配慮と一体で設計します。画像・動画・ファイル送信を初期版で持たない判断は、違法コンテンツ・マルウェア・著作権リスクを減らす点で有効ですが、テキストだけでも違法利用への対応は必要です。

未成年の年齢確認は、アカウント不要・テキストのみのv1で直ちに一律必須と結論づけられません。一方、年齢を問わず利用する設計なら、利用規約で不適切・違法な利用を禁止し、通報窓口を示し、児童の安全に関する重大な通報の取扱いを事前に決めてください。年齢制限、課金、出会い機能、画像・動画、位置情報を導入する場合は、別途の専門的な再評価が必要です。

## 6. OSSと運営サービスの責任分担

MIT Licenseは著作権上の利用許諾であり、OSS配布者の説明を、導入者が自ら第三者向けサービスを運用する際の届出・データ保護・利用者対応の代わりにはできません。コードだけを提供し、開発者のサーバー、API、ログ基盤がメッセージを一切扱わない構成では、実際にサービスを提供するself-hosted運営者が、自らの構成を確認するのが基本です。

反対に、公式の共通API、リアルタイムリレー、DB、認証、ログ、モデレーション、障害監視を提供する場合、どの組織が通信とデータを取り扱うかが変わります。提供形態を変える前に、電気通信事業、通信の秘密、個人情報、外部送信、利用規約上の主体を見直してください。

## 7. 公開判定のための最終チェック

公開ボタンを押す前に、次の質問に文書で答えられる状態にします。

1. 誰が利用者にサービスを提供し、どの問い合わせ先を表示するか。
2. 料金、広告、紹介料、スポンサーその他の収益意図があるか。
3. 送信者・受信者・サーバー・外部インフラ・ログ・バックアップのフローはどうなっているか。
4. 本文とメタデータを誰が、どの目的で、どの条件なら閲覧できるか。
5. 何を何日保存し、削除表示はどのデータ範囲を指すか。
6. 端末から誰のサーバーへ何が送られるか。第三者解析・広告SDKは本当に必要か。
7. 通報、漏えい、障害、法的要請を誰がどの手順で受けるか。
8. 届出・登録要否について、実際の構成と収益性を添えて総合通信局へ確認したか。
