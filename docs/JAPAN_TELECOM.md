# 日本で `nanne` を公開運用する場合の電気通信事業法ガイド

**調査日: 2026-08-18**

> **重要**：これは、`nanne` を日本で公開運用する場合の公開情報に基づく調査メモです。個別の届出・登録の要否を確定するものではありません。収益化の有無、実際のデータフローおよび運営主体を整理したうえで、公開前に管轄の総合通信局へ確認してください。

`nanne` のMIT Licenseはコードの利用許諾です。公式サービスを運営する者や、自らホスティングして第三者へ提供する者に課され得る法令上の検討・手続を免除しません。

## 結論

`nanne` の想定する「招待URLを知る少人数が、宛先を指定して、内容を加工せずにテキストを交換する」機能は、総務省が例示する利用者間メッセージ媒介と同じ方向の機能です。メッセージ媒介そのものは、**他人の通信の媒介**に当たり得ます。[1]

ただし、チャット機能があるだけで届出・登録が必要になるわけではありません。総務省のガイドブックは、他人のために役務を提供し、利益を得ようとし、電気通信設備を用い、反復継続して提供する場合に「電気通信事業を営む者」に該当すると整理します。無償・原価ベースで提供する場合は、この「利益を得ようとする」に当たらないと説明されています。[1]

| `nanne` の運用事実 | 現時点の整理 | 公開前の対応 |
| --- | --- | --- |
| 自己利用・開発・一回限りの検証 | 反復継続または他人の需要への提供に当たらない可能性がある。 | 公開サービスの扱いに移る前に、運用事実を見直す。 |
| 無償・広告なし・原価回収を超える利益を意図しない継続提供 | 総務省ガイドブックの「営む」要件に当たらない可能性がある。ただし、実態判断は必要である。 | 収益源、運営目的、利用規約、設備構成を記録し、判断に迷う場合は総合通信局に確認する。 |
| 有料、広告収入、紹介料その他の利益を得る意図を伴う継続提供 | `nanne` の通信形態では、登録または届出が必要な電気通信事業に該当する可能性が高い。 | 事業開始前に総合通信局へ相談し、登録対象でなければ法16条の届出を行う。 |
| OSSを配布するだけで、開発者のサーバー・APIがメッセージを通らない | コード配布者と実際の通信サービス運営者は区別して考えるのが合理的である。 | self-hosted運営者が自らの提供形態について確認する旨をREADME等に明記する。 |

この表は総務省の一般的な考え方を `nanne` の想定に当てはめたものです。**無料であること、小規模であること、Cloudflare等を使うこと、招待制であることのいずれも、単独では結論を決めません。**

## 1. なぜ `nanne` のチャットは「媒介」の候補になるか

電気通信事業法は、電気通信設備を用いて他人の通信を媒介すること等を「電気通信役務」とし、これを他人の需要に応じて提供する事業を「電気通信事業」と定義しています。総務省は、オンラインサービスでは、情報を本質的に加工・編集せず、送信時に受信者を宛先として指定する場合を「他人の通信の媒介」と説明し、メール、ダイレクトメッセージ、参加者を限定したWeb会議、ビジネスチャットを例示しています。[2] [1]

`nanne` v1 は、少人数の受信者を招待URLで特定してメッセージを届ける構想です。よって、公開タイムライン型の「場」の提供ではなく、上記のメッセージ媒介に近い前提で扱うべきです。メッセージを要約・変換・審査する機能を将来追加する場合でも、媒介性や他の規律が自動的に消えるわけではないため、仕様変更時に再確認してください。[1]

## 2. 登録・届出・適用除外の分岐

電気通信事業を営もうとする者は原則として登録を受けますが、自ら設置する電気通信回線設備の規模・区域が省令基準を超えない場合等は登録対象から除かれます。その場合であっても、電気通信事業を営む者であれば法16条の届出が必要となり得ます。[2]

総務省のガイドブックは、他人の通信を媒介するサービスを、登録・届出が必要な類型として示しています。他方、他人の通信を媒介せず、かつ電気通信回線設備を設置しない「第3号事業」や、専ら一者への提供、同一構内での提供は登録・届出を要しない類型として整理します。招待制で少人数であることは、専ら一者への提供と同義ではありません。[1] [2]

| 確認順序 | 確認する事実 | `nanne` での確認材料 |
| --- | --- | --- |
| 1 | 誰の需要に応じるか | 運営者、対象利用者、招待URLの発行者、公開範囲。 |
| 2 | 利益を得ようとしているか | 料金、広告、アフィリエイト、紹介料、寄付、スポンサー、原価回収の扱い。 |
| 3 | 反復継続して提供するか | ベータの期間、公開URL、運営・障害対応体制、利用規約。 |
| 4 | 他人の通信を媒介するか | 送信者、受信者、宛先指定、本文の加工の有無、送受信フロー。 |
| 5 | 誰が設備・回線・アプリを設置・管理するか | CDN、ホスティング、アプリ、DB、WebSocket、ログ、バックアップの構成図。 |
| 6 | 登録対象か、届出対象か、適用除外か | 上記を添えて管轄の総合通信局へ確認する。 |

## 3. 届出が必要と判断された場合

e-Govの「電気通信事業の届出」は、法16条1項に基づく、登録対象者を除く者のための手続です。**事業開始前**に行い、手数料はありません。個人・法人の別および電気通信回線設備を設置するかどうかで届出書の様式が分かれます。回線設備を設置する場合には、別途、事業用電気通信設備の自己確認の届出等が必要となる旨も案内されています。[3]

届出書の法定記載事項には、氏名・名称および住所、業務区域、一定の場合の電気通信設備の概要等が含まれます。実際の様式・添付書類・自己確認の要否は、届出時点のe-Gov案内と管轄局の指示に従ってください。[2] [3]

> 総務省は、登録・届出の照会先と提出先を、法人なら本店所在地、個人なら住所により管轄する総合通信局等として公表しています。[4]

### 相談時に渡す1枚の説明資料

公開前相談では、機能説明だけでは足りません。次のような事実を1枚の構成図と表にまとめると、登録・届出・自己確認を切り分けやすくなります。

| 区分 | 記載する内容 |
| --- | --- |
| 運営主体 | 氏名・商号、住所、問い合わせ先、公式提供かself-hostedか。 |
| 収益性 | 無料・有料、広告、紹介料、寄付、スポンサーの有無と予定時期。 |
| 通信の流れ | ブラウザ、CDN/WAF、アプリ、リアルタイム接続、DB、受信者の順序。 |
| 設備と委託先 | 各コンポーネントの運営者、リージョン、管理権限、契約主体。 |
| データ | 本文、ルームID、IPアドレス、Cookie、アクセスログ、バックアップの保存先と保持期間。 |
| 運用 | 招待URLの発行・失効、管理者による本文アクセス、通報、障害・捜査照会への対応。 |

## 4. Cloudflare・クラウドを使う場合

クラウドを使うこと自体は、媒介性や届出の検討をなくしません。総務省のガイドブックは、オンラインサービスにおいて、サービス・アプリ提供のためにクラウドを利用する事業者も、サーバーを設置する事業者に含めて説明しています。[1]

そのため、公式版の運営者は、少なくともアプリ、データベース、ログ、バックアップ、CDN/WAF、監視・エラー通知のそれぞれについて、誰が管理し、何のデータにアクセスでき、どの国・地域に保存・処理されるかを棚卸ししてください。これは届出判断と、個人情報・通信の秘密・委託先管理の判断を分けて進めるためにも必要です。

## 5. 通信の秘密と管理者アクセス

法3条は電気通信事業者の取扱中に係る通信の検閲を禁止し、法4条は通信の秘密の侵害を禁止しています。法164条3項は、同条1項の適用除外の事業を営む者についても、法3条および4条を適用すると定めます。[2]

したがって、メッセージ本文だけでなく、誰が誰といつ通信したかを推知させるログも、最小限に扱う設計が必要です。運営者が必要な場合に本文を閲覧できることを規約に一律に書くのではなく、目的・条件・権限・記録・保存期間を限定してください。

| 運用場面 | v1で決めること |
| --- | --- |
| 通常運用 | 本文を読まないことを原則とし、本文への恒常的な管理者アクセスを避ける。 |
| 通報・安全対応 | 受付方法、閲覧承認者、対象範囲、判断基準、アクセス記録、削除・停止手順を定める。 |
| 障害調査 | 本文を使わずに解決できるログを優先し、本文が必要なときの承認・記録を定める。 |
| 法的要請 | 受領窓口、真正性確認、保存措置、開示判断、専門家・関係機関への相談経路を定める。 |
| 削除 | 本文、添付が将来追加された場合の派生データ、ログ、バックアップを分けて保存期限を定義する。 |

## 6. 変更・廃止

法16条の届出後、氏名・住所等の変更は遅滞なく届け出る必要があり、業務区域または一定の電気通信設備の概要を変更しようとするときは事前の届出が必要です。事業の全部または一部を休止・廃止したときも遅滞ない届出が必要です。[2]

有料化、広告導入、公開ルーム、検索、ファイル送信、音声・映像、外部の共通バックエンド、海外向け提供などは、収益性・通信の宛先・設備・利用者情報の扱いを変え得ます。実装前に、届出事項だけでなく通信の秘密、個人情報、外部送信、利用規約を再評価してください。

## 7. OSS配布と公式サービスの切り分け

`nanne` のコードを配布するだけで、開発者のサーバー・API・ログ基盤が利用者の通信を一切扱わない完全self-hosted構成では、実際に利用者へ通信サービスを提供する導入者と、コード配布者を同一視しない整理が有力です。反対に、共通のAPI、リレー、認証、DB、モデレーション、ログ基盤を開発者側が提供するなら、実際のデータフローに基づく再評価が必要です。
